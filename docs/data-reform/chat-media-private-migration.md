# Adjuntos históricos de chat: operación pendiente de infraestructura y QA

Estado: preparación de código y pruebas locales. R21 / H3.S3.M1 / H7.S1 **no están cerrados**; esta entrega no inspecciona ni modifica MinIO real, ACL, secretos, datos remotos ni objetos. No ejecutar el bootstrap de Compose para probar este cambio: crea usuarios, configura políticas y versionado.

## Riesgo y corrección declarativa

El bootstrap anterior de `docker-compose.coolify.yml` concedía `s3:GetObject` anónimo a `users/*/chats/*`. Quitar una URL de respuestas o cifrar subidas nuevas no revoca una URL conocida de un objeto histórico en claro. Sobrescribir un objeto tampoco protege sus versiones previas.

El bootstrap revisado excluye ese recurso y conserva los demás grants existentes. Esto sólo elimina el Allow específico de chat; no garantiza la denegación de todas las claves no canónicas: los comodines S3 abarcan `/`, por lo que `users/a/chats/c/perfiles/old.jpg` también coincide con `users/*/perfiles/*`. Lo mismo ocurre con `stories` y `publicaciones`, incluso en niveles anidados más profundos. La prueba `minio-chat-public-policy.spec.ts` evalúa localmente el JSON declarado contra claves de chats antiguos, migrados y `GetObjectVersion`. Es una regresión del archivo; no demuestra que la política desplegada sea la misma.

Un operador autorizado debe revisar y exportar la política efectiva antes de aplicar la política candidata: ningún Allow anónimo puede cubrir chats mediante `bucket/*`, `users/*`, `users/*/chats/*`, `GetObjectVersion`, wildcard de acciones o un grant alternativo. Conservar la lectura autenticada de la identidad de la API; no agregar un Deny global con Principal `*` que también bloquee esa identidad. Revisar además el proxy/CDN, origen directo y cualquier regla que publique el bucket con credenciales de servicio. Invalidar o impedir cachés públicos de adjuntos históricos. Esta operación modifica visibilidad, conserva originales y versiones y no concede acceso nuevo.

## Núcleo de migración preparado

`src/modules/chat/migration/legacy-chat-media.migration.ts` exporta `migrateLegacyChatMedia`. Es un núcleo sin CLI, sin registro en Nest y sin adaptador remoto: importar el archivo no conecta a servicios ni ejecuta migraciones. Por defecto sólo inspecciona y devuelve `planned`; requiere `{ apply: true }` explícito para escribir mediante el puerto suministrado. La simulación sí necesita lectura del objeto; usar exports locales y un inventario revisado para evaluarla sin MinIO.

El puerto `ChatMediaMigrationStore` debe implementarse y revisarse antes de cualquier ejecución real:

- `read`: sólo lee claves inventariadas del bucket elegido; devuelve `null` exclusivamente ante objeto inexistente y propaga errores de red/permisos. Limitar tamaño al permitido de chat y procesar por lotes.
- `writeIfAbsent`: creación **atómica** sin sobrescritura, nunca un `stat` seguido de `put` sin condición. MIME del ciphertext `application/octet-stream`, disposición attachment y sin cache pública. Si la integración MinIO no puede garantizar creación condicional, detener el trabajo y revisar otro adaptador; no sustituir silenciosamente el contrato.
- `compareAndSwap`: una actualización SQL atómica por ID, comparando la referencia inventariada completa (propietario, conversación, proveedor, clave, URL con igualdad null-safe, MIME y tamaño), y devolviendo false si cambió. Actualiza únicamente `media_key`, `media_url = NULL` y tamaño cifrado. No modifica participantes, `revoked_at`, `viewed_at`, permisos ni conexión. El campo `media_size_bytes` ya representa bytes almacenados para subidas cifradas actuales.

Se valida que proveedor, propietario, conversación y clave coincidan. Antes de leer objetos o cambiar referencias, el núcleo contrasta la clave de chat contra todos los patrones públicos declarados y devuelve `public-policy-overlap` si empata alguno; también ocurre en dry-run y con fuentes ya cifradas. Este estado queda **bloqueado** y no cuenta como `planned`, `migrated` ni `already-encrypted`. La prueba de política exige sincronización entre los patrones del clasificador y todos los recursos Allow de lectura del bootstrap. Si la política efectiva difiere de la declarada, detener la ejecución y revisar el clasificador y las pruebas antes de migrar.

Cada overlap debe quedar inventariado, bloqueado e investigado manualmente por infraestructura: confirmar su procedencia y exposición efectiva, evaluar acceso al origen/proxy y revisar una corrección de política sin romper la identidad autenticada de la API. El núcleo no borra objetos, no cambia ACL, no revoca automáticamente nada ni marca esa fila como migración exitosa. No incluirla en un cierre de R21 hasta resolver y demostrar su denegación efectiva. El destino es `users/<sender>/chats/<conversation>/migrated-v1/<sha256 del original>.bin`; los reintentos reutilizan esa clave estable aunque AES-GCM use nonce aleatorio. Antes del CAS, se relee el destino, se autentica GCM y se compara con los bytes originales. Una copia corrupta, clave de cifrado incorrecta o conflicto de referencia detiene la fila. No se elimina ni sobrescribe la fuente; una copia huérfana válida permite reintentar. El núcleo no usa `media_url` para descargar.

El inventario debe distinguir fuentes en claro de fuentes GSCM1 ya cifradas usando procedencia confiable y respaldos, no sólo el nombre de archivo. El núcleo autentica fuentes con cabecera GSCM1 y todas las claves `migrated-v1/`; una cabecera dañada fuera de ese prefijo puede ser indistinguible de datos históricos sin cifrar. Aplicar a una fuente sin cabecera exige además `{ sourceEncoding: "plaintext" }` explícito tras revisar su procedencia; una fuente conocida cifrada usa `{ sourceEncoding: "gscm1" }`, que obliga a autenticar aun si la cabecera está dañada. Esas fuentes ambiguas deben excluirse y revisarse manualmente antes de la ejecución. Mantener una clave de cifrado estable, respaldada y separada de la rotación ordinaria del refresh token; comprobar que descifra las subidas existentes. No registrar claves, URLs de acceso, contenido privado ni secretos en evidencias públicas.

## Kill-test obligatorio antes de cerrar R21

A y B de gimnasios distintos conservan antes de desconectar una URL antigua MinIO, una URL de versión histórica, la URL de media de la API y una descarga de adjunto iniciada con I/O retardado. C nunca participó y D está bloqueado.

- Antes de revocar: A/B pueden descargar por API autenticada; C/D no. Las URLs MinIO de original y versión fallan sin autenticación tanto en origen como dominio público/CDN. Una URL que sólo devuelve ciphertext tampoco debe tener acceso público.
- Desconectar A/B o bloquear: el GET de media antiguo con sesión todavía válida falla para ambos y no devuelve bytes, redirección ni URL MinIO. La lectura iniciada debe fallar si la revocación ocurre durante el I/O antes de la segunda validación. Historial y sockets deben cumplir sus pruebas separadas. La API usa `Cache-Control: private, no-store`.
- Repetir en web/iOS/Android y reiniciar clientes. Reconectar crea una conversación nueva y no habilita claves/rutas antiguas. Probar también las claves clasificadas `public-policy-overlap` después de su resolución manual, originales sin fila, `?versionId=...`, GET con Range, HEAD y accesos desde proxy/CDN con URL guardada.

La segunda validación de participación tras leer storage reduce la carrera observada; no puede retirar bytes ya transmitidos ni prometer atomicidad entre la última consulta de permisos y el inicio de envío HTTP.
